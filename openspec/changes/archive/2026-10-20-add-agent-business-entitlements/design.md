# Design

## Context

现状只读核验：正式身份库19132/iam_identity，Agent和知识已remote接入、物理分库；旧config.yaml中“尚未切换”的文字属于历史阶段，不据此恢复旧环境。IAM当前dev、工作区规划前干净。V20及后续迁移已有resource_catalog、tenant_entitlements、资源授予边界和修订；Vue已有PlatformResourcesView、TenantEntitlementDialog、TenantRolesView及RoleEditDialog。

主规格目前仅iam-physical-separation，通用entitlement仍在活动change中。资源码约束支持冒号分段和连字符，本次业务码符合现有格式。只读搜索迁移未见专门Agent MCP/Skill角色码，清理需按实际库证明，不能假设有专用表。

## Goals / Non-Goals

**Goals:** 复用企业资源开通，交付中文业务配置、实时有效许可及root明确测试授权；按用户要求物理清理旧授权且不备份。详细契约见business-authorization-contract.md。

**Non-Goals:** 不托管MCP地址/凭据、不建立Graph编排或工具ACL、不替外部服务保证数据范围、不改知识库、不重写登录/SSO、不创建另一个root、不延长root会话或修改密码。本change仅在本仓实现，Agent代码与库由配套change负责。

## Decisions

### 1. 复用资源和权限，不建重复业务表

每业务一个agent:business:<code>资源、一项同前缀:use权限，resource kind沿用现有叶子资源，grantable_to_tenants=true。业务目录由双方冻结清单登记，当前三项见共同契约，不注册历史未公开图。目录前缀可用于Vue分组，不构成权限匹配。

继续用现有企业开通、资源授权管理资格、企业独有角色及成员角色。平台角色不携带业务权限；新增权限均精确匹配。保留一般资源回收不删除仍有效角色配置的规则，本次物理清理针对旧模型的专属对象，两者不混淆。

### 2. 业务身份继续使用现有HTTP协议

沿用iam.identity.v1.permissions及四个修订，不增加businesses令牌字段或新JWT。检查权威快照SQL、RoleAdminService、ResourceGrantSupport、授权函数、资源/权限/成员变化触发器，保证任一影响许可的改变推进对应修订。

现有执行引用复查返回active/context_matches及修订，Agent在入口持有已核实精确许可快照，逐发送复查其仍对应原修订。测试必须证实角色撤权、角色停用、权限停用、资源停用、企业回收、成员停用和A→B→A均失效；仅active检查不够。若发现遗漏，新增后续迁移修复，不改已执行Flyway历史。me、Bearer内省、浏览器会话及复查输出保持一致，不做跨请求正向缓存。

### 3. Vue沿用现有管理路径

平台企业页面按中文名开通“Agent业务”；企业角色页面单列“可用业务”，来自已开通且可授资源。保持原资源授权资格，不让企业自行开通。配置与有效权限分开展示，回收后显示失效原因，错误和409要求刷新，无自动重放写。

不再新增MCP/Skill人员授权页。涉及UI实施时先读本仓DESIGN.md、UX-CONTRACT.md及适用前端技能；当前规划不改变现有样式或代码。验收实际浏览器包括键盘、窄屏、A→B→A迟到响应及刷新持久化。

### 4. root一次配置，不做常驻旁路

提供独立运维配置命令，默认只读计划，执行阶段由协调者在用户后续实施指令范围内运行。精确定位现有root UUID，列出所有当前active企业，按企业建立缺失成员和tenant_agent_test_admin专属角色。若root、既有成员被停用或身份冲突，明确失败，不偷偷启用或创建替身。缺失的合法成员可建档。

该角色获得当前三项业务使用码及Agent现有精确运营查看、指标和受控正文权限；非业务查看权限如IAM当前未登记，应按双方既有消费者权限契约补登记并明确作用域，不把它们伪装成业务:use。root通过正常登录、切企业、角色赋权取得权限；不调用BYPASSRLS、无username==root、无agent:*通配。root原有平台管理角色保持，知识授权及无关破坏性权限不改。

命令可重入，每个企业事务包含开通、成员、角色、授权、修订与审计，无变化不重复修订。运行后的步骤检查点仅保存非秘密对象ID、版本、计数和状态，不保存旧行。此命令不挂启动生命周期，用户手动撤权后不会自动授回。未来新企业、新业务均需显式配置。

### 5. 清理对象和发布责任

IAM清理明确命中的旧Agent MCP/Skill权限定义、角色权限/服务账号关联、旧种子、旧菜单及兼容缓存。优先核对enterprise:mcp、mcp:binding:read/manage；若实际不存在，报告零项。IAM没有mcp_identity_bindings表则不创建或删其他表代替，Agent独立清理其正式业务库。

通用权限/角色/成员、resource_catalog和tenant_entitlements全部保留；知识配置保留，审计/历史migration/原验收保留。旧授权不采用disabled、deprecated表或备份schema存续。权限清理必须原子推进受影响修订和审计，避免旧执行上下文继续有效。

## Migration Plan

1. 在自建空临时身份库跑空库及旧schema升级，构造旧授权测试行验证清理、修订、失败事务回滚和无旁路；不复制正式数据，测试后回收。
2. 接实际Flyway head（当前至V23，实施时复核），新增业务资源注册及必要修订修复。部署IAM后通过root命令对明确正式企业清单完成授权；不在迁移里硬编码正式用户UUID/密码。
3. 与Agent协调短维护窗口，停止受保护新运行，Agent切新模型并验证root。IAM临时保留旧定义只允许本次发布内部窗口，不是可交付终态。
4. Agent先清理自身旧表与旧接口并确认不再请求旧码，IAM清理旧定义及关联；最后重启/重新登录并联合验证，新链路成功才开放业务。
5. 按用户明确选择，不做pg_dump、快照、影子库、backup表或旧授权导出；一项事务失败回滚该事务，提交后只向前修复，跨仓失败保持维护拒绝。不宣称一次发布具有跨库全局原子性。

执行时正式数据写入权限来自用户后续实施指令，本轮只有计划授权；无需为已明确批准的清理在后续流程人为增加重复确认。现有root凭据只在受保护本机位置使用，日志/证据不含Token或口令。

## Risks / Trade-offs

- root拥有广泛企业测试资格→每企业明确角色和切换审计，保留撤权反例，避免全局特判及永久自动授权。
- 外部MCP范围不能由IAM赋予→报告区分IAM已授全部Agent业务、Agent数据查看、外部数据可达范围，不把缺失服务端能力算已完成。
- 无备份清理不可恢复旧授权→空库演练、明确对象清单、每事务原子和向前修复；不保留旧兼容支路。
- 配套Agent尚未完成→IAM本地实施可验收，但联合发布任务保留未完成，不能用权限列表冒充模型/MCP实际运行。
